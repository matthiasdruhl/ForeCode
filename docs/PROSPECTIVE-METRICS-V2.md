# Unregistered prospective metrics v2 proposal

This additive local protocol is a new, unsigned study proposal awaiting owner review before generation or architecture selection. No existing study is migrated or reinterpreted. Frozen task, grade input/report, protected receipt and deterministic Decision Report contracts are unchanged. Software tests grant no execution, custody, disclosure or spending authority.

The original fixture implements personal bookings and has no future team benchmark adapter. A future-task authorization suite cannot observe complete future-case outcomes on that original tree before coding. Running such a baseline and declaring its absent cases passed or zero would manufacture evidence. v2 instead binds the actual verified five-check personal regression baseline and makes future authorization explicitly not applicable before the future requirement.

`prospective-tournament-metrics.v1` retains its exact schema and existing semantics: same future-suite baseline and final authorization observations remain required. `prospective-tournament-metrics.v2` adds the required literal `baselineAuthorization: not_applicable_before_future_requirement`. Registration parses this version as an independently committed new protocol; it does not silently upgrade v1. All task/source/conditions/evaluator/suite/policy identities remain prospectively bound.

For v2, each independently held baseline snapshot uses `protected-metric-snapshot.local.v2`, role `baseline`, and this authorization proof:

```json
{
  "kind": "not_applicable_before_future_requirement",
  "identity": "exact existing five-check evaluation identity object",
  "receiptSha256": "SHA-256 of that exact protected receipt"
}
```

The example describes the fields; it is not a schema-valid substitute for a real receipt. The constructor requires an actual in-process `TrustedEvaluation`, VERIFIED verdict, all five checks present and passing, and the unchanged public baseline policy. A copied JSON receipt cannot acquire that capability. The reader additionally binds the exact existing baseline run ID from the authenticated arm runtime original, original/prepared tree, fixture, baseline evaluator, suite and policy. It freshly reloads receipt bytes and independently held snapshot custody; a changed proof, role, source, receipt, policy or chronology fails closed. The baseline does not use the derived same-future-suite evaluation UUID retained by v1.

The `prospective-tournament-observations.v2` baseline authorization value is the explicit not-applicable tag. Its future authorization failure count remains **null**, never zero. Baseline static boundary measurements still require complete source coverage, no unresolved imports and all predeclared rules. Existing personal regression correctness comes from the five-check proof, not from a future authorization count.

Final snapshots retain the existing eight-check future suite, protected per-case observations and final snapshot structure. A not-applicable tag is rejected for final snapshots and for any v1 snapshot. Complete final case coverage remains required; missing, unrun or invalid cases keep the assessment unestablished. A genuine observed final failure remains a failure.

With complete boundaries, both terminal attempts and complete final case observations, the calculator assesses the strict predeclared direction: B final forbidden edges must be fewer than A final forbidden edges. A 0/0 tie contradicts that direction. Final authorization is a separate gate: a boundary prediction can be supported while authorization preservation is false; this never issues an adoption recommendation or overrides the deterministic report. The calculator always reports unauthenticated calculation provenance. Only the protected reader's independently authenticated chain can support a private supplementary observation. N=1 does not establish generalization or Meta's incremental contribution.

The reserved unsigned packet goal explicitly names `B_fewer_final_forbidden_edges_than_A`, the candidate-neutral forbidden pair `src/server/http.ts` to `src/server/booking-store.ts`, preparation effort and final-only future authorization. The original fixture has no forbidden direct edge for that pair; preserving 0/0 will contradict the strict prediction. No favorable result is promised. The initial boundary rule, exact final authorization case selection and semantics still need owner/evaluator review and independent initial holding before inference or selection.

Focused validation uses synthetic keys, receipts and inert trees only. New v2 tests cover null baseline counts, strict ties, final failures, missing/invalid final evidence, version/role/tag rejection, actual five-check proof requirements, cloned/failed/incomplete receipts, and independently reheld source/receipt/evaluator substitutions. Existing v1 metric suites retain their JSON and passed unchanged. No genuine study, provider call or grader execution was performed to validate this protocol addition.
